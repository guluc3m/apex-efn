# ADR-205: Schema v1 conventions and integrity guards

## Status

Accepted on 2026-11-09 by the repository owner, who waived the Tech Lead gate for the DEV-2 tasks. The TL has
not reviewed it and may amend or reverse it with a 900-range ADR.

## Context

The scaffold `apps/web/prisma/schema.prisma` did not follow the spec. Money columns were `Int` (int32
overflows at about 21M EUR in cents), FX rates were `Float`, and currencies were free strings.
`SigningKey.ownerId` and `Decision.decidedBy` were foreign keys to `User`, so service keys and automatic
decisions could not be stored. Configuration was a single mutable `TenantConfig` row, and several spec §6
entities were missing.

ADR-201 makes Prisma Migrate the only owner of DDL, and SQLAlchemy (D2-05) maps the same tables. Both sides
need one set of conventions.

## Decision

### Column conventions

- **IDs** are `text` and are generated by the application (ULIDs from `apex.common.ids`), with no database
  default. Seed rows use readable fixed IDs (`tenant-a`, `user-owner-a`). Tenant IDs match the Keycloak
  `tenant_id` claim.
- **Money** is a `bigint` `<name>_minor` column next to a `Currency` column. The Postgres enum `Currency` is
  closed to `EUR | USD | CNY`. Floats are never used for money.
- **FX rates** are `numeric(24,12)`. Statistics (MAD, z-scores, MCDA weights and contributions) are `numeric`.
  Ratios in `[0, 1]` that come from platforms are `numeric(7,6)`. Business percentages are basis points (`int`).
- **Timestamps** are `timestamptz(6)` with no `now()` default and no `@updatedAt`. The application injects the
  clock (AGENTS.md rule 0.6), so every timestamp is written explicitly.
- **Actors** are polymorphic: `<role>_type ActorType(human | service | agent)` plus `<role>_id`. Columns that
  can only hold a person (`approver_id`, signing session `user_id`) stay foreign keys to `users`.
- **`config_version`** is the integer tenant config version of ADR-400. Rows that record an engine result
  (`seller_confidences`, `price_sanity_checks`, `financial_fits`, `scores`, `recommendations`, `missions`)
  have a composite foreign key `(tenant_id, config_version)` to `tenant_config_versions`, so a result can
  never point at a configuration that does not exist.
- **Converted amounts** keep their origin: `original_amount_minor`, `original_currency`, `fx_rate`, `fx_as_of`,
  `fx_source` and `converted` (spec 3.5.1, criterion 24).
- Every tenant-scoped table has `tenant_id`, including child tables (`financial_rows`, `score_breakdowns`,
  `negotiation_messages`). D2-04 adds the RLS policies on exactly these columns.

### Global tables

These have no `tenant_id`: `users` (membership is per tenant), `sellers`, `seller_platform_ids`,
`seller_signal_snapshots` (raw platform facts are the same for every tenant) and `fx_rates`. Seller
**confidence** is per tenant, because it depends on the tenant's `seller.*` configuration. `signing_keys`
and `llm_events` have a nullable `tenant_id`: service keys and calls made outside a tenant (evals) are global.

### Configuration entities

The spec lists `PricingThresholdConfig`, `ConfidenceModelConfig` and `ScoringWeightsConfig` as separate
versioned entities. ADR-400 resolves configuration as one document with one `config_version`, and engine
outputs carry that single number. So:

- `tenant_config_versions` stores the tenant layer of that document, including category overrides. The
  `sanity.*` section is the PricingThresholdConfig and the `seller.*` section is the ConfidenceModelConfig.
  There are no separate tables, so the two can never disagree on the version.
- `user_profile_preferences` is the ScoringWeightsConfig: append-only versions per `(tenant, profile_key)`
  with MCDA weights, negotiation parameters and hard constraints.
- Each version points at the signed `decisions` row that created it. Only the seeded baseline has no decision.

### Integrity guards (migration `integrity_guards`)

Prisma cannot model these, so they are raw SQL in a migration (ADR-201):

- **Append-only** (`UPDATE`, `DELETE` and `TRUNCATE` raise): `audit_events`, `signatures`, `fx_rates`,
  `seller_signal_snapshots`, `seller_confidences`, `tenant_config_versions`, `user_profile_preferences`,
  `financial_rows`.
- **Financial snapshots** are created already `active` by the activation decision. The only allowed update is
  `active -> superseded`, which sets `superseded_at` once. At most one active snapshot per tenant (partial
  unique index). Deleting a snapshot is forbidden.
- **Financial imports**: everything except `status` is immutable. Allowed moves are `draft -> active | rejected`
  and `active -> superseded`. Only drafts can be deleted.
- **Decisions**: the canonical payload and every other column except `status`, `signed_at` and `rejected_at` are
  immutable. Only `pending_signature` decisions can change. Decisions are never deleted.
- **CHECK constraints**: human keys belong to their user and tenant; human signatures need a signing session
  and `auth_at`; `alg = 'Ed25519'`; payload hashes are lowercase hex SHA-256; `required_signers` is 1 or 2;
  decision status agrees with its timestamps; a signing session window is positive; FX rates are positive;
  financial rows follow spec 3.1.1 (one of `value_minor` / `value_bp`, a currency exactly with an amount,
  `YYYY-MM` periods, budget rows have a category); seller confidence `score` is in `[0, 100]` and is null
  exactly when the band is `insufficient_data`; an `agreed` negotiation outcome has a final price; a gate item
  has at least one cause and is resolved exactly when it has a resolution.
- Guard errors raise SQLSTATE `23000` with a message starting with `apex:`. CHECK failures keep their standard
  codes (`23514`).

GDPR erasure (D2-12) will need a controlled path through these guards. That path gets its own ADR, and the
guards are not weakened in the meantime.

### Embeddings

`pgvector` is enabled. `product_embeddings` and `negotiation_embeddings` store `vector` without a fixed
dimension, together with `model` and `dimensions`, because the embedder is a configurable self-hosted model
(spec 5.6). An ANN index needs a fixed dimension, so it is added per model in a later migration once the
embedder is chosen.

### LangGraph schema

The `integrity_guards` migration creates the empty `langgraph` schema (ADR-201). The checkpointer's `setup()`
creates its tables there.

### Seed

`apps/web/prisma/seed.ts` creates `tenant-a`, `tenant-b` and the ten Keycloak users with their memberships.
It is idempotent and uses a fixed timestamp. It runs with `node prisma/seed.ts` (Node 22 strips the types).
Tenant configuration is loaded afterwards by `python -m apex.tenant_config.load_defaults` (D4-03).

## Consequences

- SQLAlchemy models (D2-05) must use `BigInteger` for `_minor` columns, `Numeric` for rates and the same enums.
- Application code must set every timestamp and ID itself. A missing value fails loudly at insert time.
- Tests that clean up data cannot `TRUNCATE` guarded tables. They use a fresh database per test module
  (`apps/orchestrator/tests/db/conftest.py`).
- Known differences from the D2-01 contract go into the D2-01b follow-up: `NegotiationOutcome.final_price` is
  required in the contract but has no value when the outcome is not `agreed`.
